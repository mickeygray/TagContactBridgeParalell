# The Logics ActivityReport — what you can actually read from it

A terms dictionary, built from a real pull: **45,582 rows, 2026-07-01 → 2026-07-28,
domains TAG + WYNN + AMITY.** Every count below was measured, not estimated.

Regenerate the underlying material any time:

```bash
node scripts/activity-vocab.js --from 2026-07-01 --to 2026-07-28
```

That writes to `runtime/vocab/`:

| File | What it's for |
|---|---|
| `activity-rows.tsv` | every row, one per line — **grep this**, it's the workhorse |
| `activity-subject-shapes.json` | subjects with digits masked to `#`, by frequency |
| `shapes-ge2.txt` | the 317 shapes covering 98% of rows |
| `activity-field-census.json` | every field, fill rate, distinct count |
| `activity-categoricals.json` | full frequency for `Type`, `CreatedBy`, domain |

The report is **prose**. There is no schema behind `ActivitySubject` — staff type into
it. That is why grep, not a parser, is the honest instrument for an unfamiliar question,
and why the alias splits below exist at all.

---

## 1. The shape of the thing

Ten fields. That's all there is.

| Field | Fill | Distinct | What it is |
|---|---|---|---|
| `CaseID` | 100% | — | the case. **Not unique per row** — a case has many rows |
| `ClientName` | 100% | — | client display name |
| `Type` | 100% | 18 | a category — **unreliable, see §4.1** |
| `ActivitySubject` | 100% | 2,405 | the payload. Free text. Everything lives here |
| `Created` | 100% | — | when the activity happened |
| `CreatedBy` | 100% | 60 | who — **81% is a service account, see §4.2** |
| `TaskOrActivity` | 100% | **1** | always the literal `"Activity"`. Carries no information |
| `LastModifiedDate` | 87% | — | when the row was last touched |
| `LastModifiedBy` | 87% | 19 | who last touched it |
| `__domain` | 100% | 3 | added by our puller, not Logics: TAG / WYNN / AMITY |

**The range is native.** One API call covers any span — a whole month is one call per
domain, about ten seconds. Don't loop days.

**The API caps at 50,000 rows and truncates silently.** `liveGatherService` splits any
window that comes back at the cap and re-pulls until every piece is under it. A capped
window is a partial answer wearing a complete one's clothes.

**The window filters on `LastModifiedDate`, not `Created`.** Measured on the July pull:
45,336 rows (99.5%) were genuinely created in July; **246 rows were created earlier**
— back to 2021 — and swept in because someone touched them. If you pull two adjacent
months and add them up, those 246 are counted twice.

**The same range does not re-answer identically.** Two pulls minutes apart returned
33,560 and 33,559 TAG rows. Nothing was wrong either time — the modified-date window
moves under you. Never present a row count as an exact, reproducible fact.

## 2. What the rows actually are

This is the single most important framing fact, and it surprises people:

| Rows | Share | What |
|---|---|---|
| 31,412 | 68.9% | **lead ingestion** — `Case received from …` |
| 5,521 | 12.1% | `Case updated by Public API` |
| 2,238 | 4.9% | documents |
| 1,459 | 3.2% | other |
| 1,297 | 2.8% | money |
| 1,182 | 2.6% | SMS |
| 940 | 2.1% | tasks |
| 699 | 1.5% | assignment |
| 548 | 1.2% | status changes |
| 187 | 0.4% | soft pull / credit |
| 99 | 0.2% | calls logged in Logics |

**81% of the report is machinery.** Leads landing and API syncs.

33,018 distinct cases were touched in July — but **31,412 of them are nothing but a
lead arriving**. Real casework happens on roughly **1,600 cases**. Any metric with
"cases" in the denominator has to say which population it means, or it is off by 20×.

## 3. Reading a range

```bash
# what kinds of thing happened
awk -F'\t' '{print $3}' runtime/vocab/activity-rows.tsv | sort | uniq -c | sort -rn

# anything mentioning a concept, regardless of how it was typed
grep -iE "soft ?pull|transunion" runtime/vocab/activity-rows.tsv

# one case's whole story, in order
awk -F'\t' '$2=="429441"' runtime/vocab/activity-rows.tsv | sort -t$'\t' -k4
```

Columns are `domain, caseId, type, created, createdBy, subject`.

## 4. Term families

278 terms, mapped from the July 2026 pull and grouped by family.

**Confidence is the analyst's own and is not uniform.** `observed` means the
meaning is evident in the data or defined in repo code; `inferred` is a reasonable
reading with nothing confirming it; `uncertain` means genuinely unknown. Treat
anything below `observed` as a lead, not a fact — and check a number before you
put it in front of anyone.

Regenerate with `node scripts/build-terms-doc.js`.

## 5. Combinations you can read

The report is one table, so anything that shares a `CaseID` can be joined. These are
worked examples — each was actually run against the July pull, and each carries the
caveat that came with it.

### Soft pull → did they buy?

151 cases had a soft pull in July; 139 produced a usable score; 69 of those (50%) also
have a payment.

| Score band | Pulled | Paid | Rate | Declines |
|---|---|---|---|---|
| <550 | 31 | 12 | 39% | 7 |
| 550–619 | 29 | 19 | 66% | 5 |
| 620–679 | 35 | 17 | 49% | 3 |
| 680–739 | 25 | 14 | 56% | 3 |
| 740+ | 19 | 7 | 37% | 0 |

**Read this carefully.** Conversion does *not* rise with score — 550–619 converts best
and 740+ converts worst. At 19–35 cases per band that is well inside noise, and the
honest statement is "no usable relationship at July volumes."

The **declines** column is the real signal: 7 → 5 → 3 → 3 → 0 as score rises. Low
scores don't buy less, they *fail to pay* more. That is a payment-plan risk question,
not a qualification question.

### Documents vs money

166 cases have both a document and a payment. Documents came first on 108, payment
first on 58 — so roughly a third pay before sending anything in.

### Status churn

332 cases moved status at all in July; 47 moved three or more times; one case moved 12
times. Churn is a workload signal, not a progress signal.

### Two joins that will lie to you

**Velocity.** Lead-arrival → first-payment looked like a median of 9.9 days. It is not.
Only **15 cases** had *both* events inside the 28-day window, because most cases that
paid in July arrived earlier. A within-range join **silently selects for speed** — a
case that took 40 days to close cannot appear in a 28-day window at all. Any
"time to close" figure needs a lookback wider than the thing being measured.

**SMS consent.** 267 cases were texted; 190 have no consent row in range. That reads
like a compliance problem and almost certainly isn't — consent was granted before the
window opened. **Absence of an event in a range is not absence of the event.**

Both are the same mistake: treating a window as a world.

## 6. The gotcha index

Ranked by how much money a naive read could cost.

1. **`Type` misses 43% of soft pulls.** 184 rows mention a soft pull in the subject;
   only 104 carry a soft-pull `Type`. The other 80 are typed `General`.
   **Filter on the subject, never on `Type`.**
2. **Score `0` is not a credit score.** 12 pulls returned `0` (no score — thin file,
   frozen, or no hit) and one says `FROZEN` outright. Averaging them in drags the mean
   from **635.2 to 593.3** — a 42-point error.
3. **`CreatedBy = "Mickey Gray"` is the API service account,** not the person. It
   authored 36,961 of 45,582 rows; 36,932 of those are lead ingestion and Public API
   syncs. Counting it as staff activity makes one "person" 81% of the company.
4. **68.9% of rows are lead ingestion.** Any per-case or per-row rate needs to say
   whether its denominator is all 33,018 touched cases or the ~1,600 with real casework.
5. **Alias splits.** The same thing spelled several ways, each splitting a count:
   - soft pull → `1SOFTPULL` · `iSoftpull` · `iSoft Pull` · `SOFT PULL` ·
     `SOFTPULL-` · `Isoftpull Transunion` · `PER SOFTPULL FICO SCORE` · `Credit Score`
   - `[RESO ONLY]-RESO ONLY RESO ONLY` vs `…RESO ONLY RESO ONLY RESO ONLY` (30 + 5 rows)
   - `Jacqueline Santos` vs `Jacqueline  Santos` (double space — 158 + 21 rows)
6. **The window filters on `LastModifiedDate`.** 246 July-pulled rows were created
   earlier, back to 2021. Adding adjacent months double-counts them.
7. **The same range doesn't re-answer identically** — 33,560 then 33,559 TAG rows
   minutes apart. Don't quote a row count as exact.
8. **The API caps at 50,000 rows and truncates silently.** Always pull through
   `liveGatherService`, which splits and re-pulls; never call the endpoint raw.
9. **`TaskOrActivity` is always `"Activity"`.** All 45,582 rows. It looks like a
   discriminator and is not.
10. **Not every score is TransUnion.** `Credit Score: 477 Exp` is Experian. Bureaus
    aren't interchangeable.
11. **Calls in Logics are not the call record.** Only 99 rows. The real call data is
    CallRail and RingCentral, outside this report entirely.
